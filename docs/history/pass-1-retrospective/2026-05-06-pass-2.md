# Pass 2 — If We Started Over

**Date:** 2026-05-06
**Scope:** speculative architectural and process reflections imagining a fresh start with full hindsight. Treats the current implementation as a working reference.

This document is for future-self or for anyone re-implementing _World Builder's Handbook_ in another language. It assumes you have read the lessons-learned doc.

## Decisions worth keeping verbatim

These were the right call the first time and would be the right call again:

### Go, not Python

The data shape is "lots of small, typed lookup tables, each with a WBH page citation, with strict precision requirements on numeric outputs." Go's compiled-in literal tables, native typing, and zero-packaging surface area beat Python's dynamic flexibility in this domain. The Python false start cost one task of scaffolding and surfaced a real macOS/Python 3.12 editable-install bug. Don't re-litigate.

### Deterministic Roller as the load-bearing seam

`roller.Roller` interface with `Seeded` / `Scripted` / `Fixed` impls. Every dice roll passes through it; no package-level RNG anywhere. A seed plus a sequence of options fully determines a system. `Scripted` panics on exhaustion. Worked from day one through the entire project unchanged. **Pass-2 verdict:** keep exactly. This is the project's architectural keystone.

### Worked-example regression tests

The book threads in-line examples through every chapter. Encoding each with `roller.NewScripted(...)` driven by the book's exact dice and asserting every output to the digit is the most valuable testing pattern. **Pass-2 verdict:** keep, and consider extracting the Zed pipeline builder into a non-`_test.go` shared helper from the start (rather than factoring it partway through, as we did during the Markdown sub-project's golden-file work).

### Tables as Go literals with WBH page citations

Compiled-in literals, `*float64` for nullable cells, line comments citing the source. **Pass-2 verdict:** keep. The temptation to externalize tables to YAML/TOML never paid for itself across ~30 sub-projects.

### Brainstorm → spec → plan → TDD-with-subagent-review

The chapter-sized decomposition gave each sub-project its own clean cycle, captured book-inconsistency notes, and documented carry-forwards. Per-task two-stage review (spec compliance + code quality) caught real bugs. **Pass-2 verdict:** keep the workflow exactly. The subagent dispatch overhead was paid back many times over by per-task review catches.

### Modernizer-as-mandatory gate

Running `go fix ./...` first in `task check` and failing if it produces any diff turned modernizer hints into a hard signal. **Pass-2 verdict:** keep, and add it to the project template even before the first task.

### Surfacing book inconsistencies as memory entries

Six independently-documented WBH inconsistencies preserved as memory entries with explicit citations. The code is honest about which interpretation it picked and why. **Pass-2 verdict:** keep, but extract a centralized `docs/wbh-inconsistencies.md` from the start (see "Things to do better" below).

## Decisions worth revising

### Class IV-P as plain text from the start

`RenderIISSClass4P` returned a string while Class 0/I and Class II/III returned structs. This asymmetry forced the Markdown sub-project's Q1 redesign mid-plan-writing. Had Class IV-P been a struct from the start, the Markdown formatters would have been uniform and the JSON path could have included it. **Pass-2 verdict:** make all three forms structs from the start. Plain-text rendering then becomes one of multiple consumers of the same struct, alongside Markdown and JSON.

### Single `worlds/markdown.go` accumulating multiple form renderers

The file ended at 419 lines holding both Class IV-P (PART P + PART P.B) and Class II/III renderers. Code-quality review correctly flagged this as a smell. **Pass-2 verdict:** split per form from the start: `worlds/markdown_class23.go`, `worlds/markdown_class4p.go`, `worlds/markdown_system.go`. Each file holds one rendering context. The duplication of `emDashIfEmpty`/`floatNonZero` helpers across `stars/markdown.go` and `worlds/markdown.go` is fine — packages own their helpers.

### `SurveyForm.ClassI bool` dead field

Declared but never written or read anywhere. Pre-existing in the code before the Markdown sub-project. **Pass-2 verdict:** define the field's meaning at the moment it's added or don't add it. Boolean flags whose semantics were never decided are pure tech debt.

### `IISSClass23Header.SectorLocation string` then `splitSectorLocation`

The header carries `SectorLocation` as a single string and the implementation splits it on `" | "`. Should have been two fields (`Sector`, `Location`) from the start. **Pass-2 verdict:** structured fields beat structured strings. The split function is small but every caller has to know about it.

### Inline modernizer-clean-tree workflow friction

Subagents repeatedly hit `task check` failure not because `go fix ./...` produced changes but because the modernize gate compares the working tree against `HEAD` and refuses to proceed with any uncommitted Go diff. The cure was always "stage your changes first, then re-run" — but it surprised every subagent the first time. **Pass-2 verdict:** either rewrite the modernize recipe to compare against the current diff (not HEAD), or document the workflow expectation prominently in `CLAUDE.md`. The current behavior is correct but its error message ("ERROR: go fix ./... produced changes") is misleading.

### Embedding chain depth

`Slot → AnomalousSlot → Placement → DetailedPlacement` is four levels of struct embedding. Works but the deeper levels become awkward (e.g., setting `dp.Body` requires `dp.Body = X` which traverses through to the embedded `Placement.Slot` — fine for Go but confusing for readers). **Pass-2 verdict:** flatten to two levels. Embed `Slot` directly into `DetailedPlacement` and accept some field duplication.

## Things to do better

### Centralize book-inconsistency findings from day one

Six memory entries documenting WBH inconsistencies. Each is well-cited. But finding them all requires knowing memory exists and that they're scattered across separate files. **Pass-2 action:** create `docs/wbh-inconsistencies.md` on day one. Each finding gets a section: page reference, divergent sources, our interpretation, why. Memory entries can then be one-liners pointing to the doc section.

### Anti-pattern checklist baked into the spec template

The "moon-path silent-zero" anti-pattern recurred four times across consecutive sub-projects. Each time it was caught in review. **Pass-2 action:** maintain `docs/anti-patterns.md` with a checklist that every new sub-project's spec must cite before merge. Include moon-path-must-iterate-too, silent-zero-vs-explicit-placeholder, modernizer-clean-tree workflow, etc.

### Toolchain decision as a day-one artifact

The `just` → `task` migration sat as uncommitted working-tree changes through most of a session. Subagents reported false positives because the underlying `task` runner was working but the `justfile` was deleted. **Pass-2 action:** pick the toolchain on day one and don't migrate mid-project. If migration becomes necessary, it gets its own committed sub-project before any unrelated work proceeds.

### Test fixture extraction from the start

The Zed `SystemDetail` builder was inline in `worked_examples_test.go` for most of the project's life. The Markdown sub-project's golden-file test had to either factor it out (invasive) or duplicate the dice script (lazy). The implementer chose a third path: external test package (`worlds_test`) reusing `composeZed()` via Go's test-package-coupling rules. **Pass-2 action:** extract a `worlds.BuildZedFixture(t *testing.T) (SystemDetail, stars.System)` helper in a non-`_test.go` file from the first sub-project. Any test that needs a fully-built Zed reuses one path.

### Don't carry uncommitted state across sub-projects

A general principle but bit us specifically with the `just` → `task` migration. **Pass-2 action:** at the start of any sub-project, `git status` must be clean. If the working tree has uncommitted changes, address them in their own sub-project first.

## Process reflections

### Sub-project decomposition was excellent

Stars (pp.14–35), 2A (pp.38–43), 2B (pp.36–38, 43–52), 2C (pp.53–67), 3A1, 3A2a, 3A2b-temp, 3A2b-rederive, 3B-geology, 3B-biology, 3B-final, IISS Class IV-P PART P.B, Markdown output. Each chapter-sized; each with brainstorm/spec/plan/implementation. Some sub-projects (3A2b, 3B) were further split into 2 or 3 nested sub-projects when the chapter was too dense for one cycle. **Pass-2 verdict:** keep this exactly. Chapter-or-section-sized is the right granularity.

### PDF-as-source-of-truth, gitignored

Place a local copy of the WBH PDF at `docs/World Builders Handbook.pdf` (gitignored — copyright). Specs and plans reference page numbers freely. The PDF lives outside version control but inside the project tree. **Pass-2 verdict:** keep.

### The library is the artifact; the CLI is a thin renderer

CLAUDE.md states this explicitly. `cmd/wbh` is one screen of code (now ~80 lines after the Markdown wiring). All real logic lives in `stars/` and `worlds/`. **Pass-2 verdict:** keep. A future webservice would slot in alongside `cmd/wbh` without restructuring.

### Two-week-equivalent path

From "stars only, single primary" to "full system with all three IISS forms emitted as Markdown" took roughly two real weeks of intermittent work, decomposed into ~30 sub-projects. The pace felt like the right balance between "one big push" (would have lost fidelity) and "incremental forever" (would have lost momentum). **Pass-2 verdict:** keep the cadence; it's not the calendar that matters but the per-sub-project review density.

## Aspirational architecture

Things that would be cleaner in pass 2 but aren't worth retrofitting:

- **All three IISS forms as structs from day one** (see "Decisions worth revising"), enabling JSON parity for Class IV-P.
- **Output renderers as a uniform interface** (`Renderer{ToMarkdown, ToJSON, ToPlainText}`), not three sibling functions.
- **A `wbh.Verifier` package** that runs all worked-example regression tests as a public API, so a future webservice can expose `/verify` endpoints.
- **Coverage instrumentation in `task check`** — `go test -cover ./...` with a minimum-coverage threshold per package.

None of these block anything. They're how Pass 2 would look architecturally cleaner without changing the project's behavior.

## Closing

The first pass shipped. Both halves of the stated done criteria are met. The codebase is faithful to the book within documented limits. The retrospective shows where polish remains and where Pass 2 would invest differently — but the first pass was good enough that Pass 2 isn't urgent. If anyone re-implements WBH in another language, this doc plus the lessons-learned doc plus the public repo at `github.com/philoserf/world-builder` should be a complete starting kit.
